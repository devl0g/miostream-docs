# SQL
1. Всі назви функцій (`now`, `coalesce`, `count`) пишемо у нижньому регістрі, тим часом інші PostgreSQL/SQL ключові слова - у верхньому.
1. Назви таблиць вводяться з її схемою, без лапок.
1. У запитах, де зобов'язують нас вводити повні назви таблиці при використанні полей (як от запити JOIN) слід використовувати 
    аліаси і скорочувати назви таблиць до декількох символів.
1. **Правило зайвих пробілів:** ми скорочуємо пробіли у місцях між назвою чогось/ключовими словами та дужками у statements. Приклади:
    `PRIMARY KEY(field1, field2)`, `CREATE TABLE public.table(...)`, `INSERT INTO public.table(...) VALUES(...)`.
1. `anime_list_units` часто скорочується як `list_units`, а його еліас зазвичай `lu`.
1. Хорошою практикою є повтор назви сутності у назвах полей, але без надмірного прояву. Приклади:
    `id -> anime_id`, `id -> user_id`, `status -> list_unit_status`, `name -> episode_name`.
1. Головним правилом name casing є snake_case, але назви функцій SQLc (значення параметру name) пишуться в PascalCase.
1. Перенесення conditions на декілька рядкуів відбувається таким чином, що логічні оператори знаходяться на початку нових рядків, а не вкінці старих. Приклад:
    `user_id = "..." AND\nstatus = "active"` замінити на `user_id = "..."\nAND status = "active"`.

# TypeScript
1. Віддаємо перевагу interface замість type у більшості випадків.
1. Імпорти повинні уникати розширення (`.ts`, `.js` і тд). Приклад:
    `import { helloWorld } from "./helloWorld.ts"; -> import { helloWorld } from "./helloWorld";`.
1. Імпорти повинні використовувати подвійні лапки для шляхів. Приклад:
    `import { helloWorld } from './helloWorld'; -> import { helloWorld } from "./helloWorld";`.

# Fastify
1. У контролерах ми використовуємо саме назви `request`, `reply`, `fastify`, `done`.
    ```ts
    const myController = (request: FastifyRequest<{}>, reply: FastifyReply<{}>) => {};
    ```
1. У контролерах обов'язковими параметрами є лише `request`, `reply`, а `fastify` та інші скорочувати.
1. Віддаємо перевагу `request.server` замість `fastify`.
1. Логери викликаємо від найближчого об'єкту, а не дальнього. Приклад:
    `request.server.log.info(...) -> request.log.info(...)`.
1. Ми використовуємо optional generics в FastifyRequest та FastifyReply, щоб вказати що приймає, а що видає запит.
    Якщо запит нічого не приймає залишаємо `FastifyRequest<{}>`.
1. Віддаємо перевагу асинхронним функціям ніж використання параметра `done`.
1. Сутності згадані в шляхах ендпойнтів мають бути в однині (`/user/`, `/anime/`).
1. Tags у схемах мають бути в однині з малої літери (`tags: [ "anime" ]`).
1. Повідомлення помилок повинні бути загальними, а текст не повинен містити динамічних данних. Приклад:
    `SELECT query couldn't receive user's information -> database read error`.
1. Повідомлення помилок повинні згадувати домен помилки, як от S3, Database, Validation і тд.
1. Віддавати перевагу нижньому регістру у повідомленні помилок.

# Backend
1. У нас Domain-based структура проєкту.
1. Віддаємо перевагу використанню camelCase у назвах змінних, функцій, методів.
1. Віддаємо перевагу PascalCase у назвах інтерфейсів, класів.
1. Віддаємо перевагу SCREAMING_SNAKE_CASE у назвах констант.
1. Файли у модулях API та CDN називаємо у форматі `<модуль_однина>.<патерн_однина|errors>.ts`. До прикладу:
    `anime.service.ts`, `anime.repo.ts`.
1. Якщо у нас декілька репозиторіїв чи треба декілька файлів сервісів, то створюємо окрему папку `services` чи `repos`. А файли всередині
    у форматі `<назва_однина>.<патерн_однина|errors>.ts`. До прикладу:
    `avatarS3Bucket.repo.ts`, `roomRedis.repo.ts`.
1. Кожен модуль повинен містити `<модуль_однина>.plugin.ts`.
1. Використовуваними патернами є `repo`, `service`, `plugin`, `schema`, `dto` , `controller`, `errors` (єдиний у множині).
