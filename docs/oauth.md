# Криптографічна частина OAuth2

OAuth2 оперує двома токенами: access та refresh. Тут детальніше розберу, що та як ми будемо використовувати для їх генерації, зберігання.
Також нам треба генерація state для запобігання CSRF атак.

## Access Token

Зумовлено, що він має генеруватися за участі верифікації Refresh Token, містити у собі пейлоад (інформацію користувача) та бекенд має мати змогу підтвердити, те
що це він його згенерував (тобто верифікація підпису). Він матиме короткий цикл життя (через ризики компроментації).

Отже, сам токен має генеруватися через `PASETO v4.p`. PASETO використовує асиметричні алгоритми підпису, тому тут треба два ключа: один (приватний) який 
генерує токен, другий (публічний) який верифікує його. Обидва мають зберігатися у .env бекенду. Пейлоад при цьому має містити у собі інфу юзера, щоб швидко 
відмальовувати його публічну інфу при завантаженні сторінки (нікнейм, ім'я, аватарка).

Обов'язково має бути exp з 15 секундами.

## Refresh Token

RefreshToken має бути чистим рандомом (криптографічним). Оскільки він має зберігатися у таблиці sessions та у кукісах користувача (у вигляді base64url), то
компрометація БД означатиме отримання доступу до всіх акаунтів (хакер зможе просто скопіювати собі якийсь токен та поставити у кукіси). Тому треба алгоритм
на бекенді, щоб він розмежовував токен який є у користувача та токен який є у БД (маю на увазі, що це один і той самий токен, але нам треба його два різні варіанта) 
та міг відтворити з клієнтського токена той токен, що є у БД (для швидкого пошуку по БД).

Раніше моїм варіантом було блочне шифрування (типу AES), щоб юзер міг дати свій токен, бекенд його зашифрував/розшифрував і отримав той токен, що у БД.
Але оскільки у нас все-таки немає такого, що з токена БД нам треба отримувати токен юзера, то шифрування буде зайвим. Значить нам треба хешування.
Проте в хешування є проблеми:
- Хакер може взяти свій набір рандомних символів і самому згенерувати та поставити хеш у нашу БД для будь-якого користувача (тобто нам треба якийсь секрет/ключ,
    який буде знати тільки бекенд, щоб він міг генерувати по ним хеші).
- І навіть так, хакер може знайти там свою сесію переставити його місцями з будь-яким іншим користувачем (тобто треба прив'язка токена до ID сесії).
- І навіть так, хакер може просто переставити значення user_id у таблиці sessions і так отримає доступ до користувача (тобто треба прив'язка токена до User ID).

Отже, рішення таке: ми беремо HMAC та SHA-512 (він краще за SHA-256, особливо на 64-біт системах), витягаємо з кукісів юзера його рефреш токен та ID сесії.
Беремо це ID сесії та йдемо у БД, щоб отримати хеш токена та userId. І генеруємо `HMAC-SHA512(k, sessionId || userId || b64urlDecode(refreshToken))` (refreshToken тут отриманий від юзера)
та порівнюємо два хеші (crypto.timingSafeEqual).

Ендпойнт який видає accessToken має бути захищений від запиту з стороннього домену. Думаю ввімкненого CORS (щоб зловмисник не отримав токен) разом з флагами SameSite=Strict,
HttpOnly, Secure (щоб генерація взагалі не відбулася) у кукісах refresh token вистачить для запобігання цього.

### Довжина даних

- HMAC ключ - 64 байт, у .env буде зберігатися у вигляді hex, тому 128 символів
- HMAC пейлоад (головне все у big-endian): sessionId (BIGINT) буде 8 байт, userId (UUID) буде 16 байт, refreshToken 32 байти, разом 56 байти
- refreshToken клієнта - 32 байт, але у вигляді b64url буде 43 (краще без падінга)
- refreshToken БД - 64 байт

## State

State допомагає запобігати CSRF. Вперше його треба застосувати на редірект ендпойнті (яка перенаправляє юзера) та у цьому ж ендпойнті записати nonce в кукіси.
Далі, коли юзер повертається на наш callback ми маємо звірити очікуваний state з тим що він приніс. Розмір нонсу прийнято брати 32 байти (43 символи b64url).

У state також варто додати назву провайдера та відокремлювати назву провайдера від підпису, треба буде у пейлоад 
підпису також додавати провайдера. Якщо так підсумовувати, то виходить state має утворюватися таким шляхом:

`state = provider || "_" || HMAC(k, provider || "_" || nonce)`

Після успішного колбека треба видаляти кукіс.

HTTP нюанси: кукіси нонса мають мати режим SameSite=Lax, HttpOnly, Secure.

Нюанс: provider не повинен містити _ у своєму слагу, треба зробити для цього окрему перевірку в коді.
